## Check GDScript lint and formatting

From a feature checkout with uv installed, run `uv run --locked --script tools/check_gdscript.py`. This uses the same gdtoolkit 4.5.0 linter, 100-column formatter and dependency lock as CI. The command compares your working tree (including new scripts) with the common ancestor of HEAD and `origin/main`. Use `--base REV` for another baseline. CI checks the PR against its target or the push against the previous revision. Run `bash tools/test_gdscript_style.sh` for the passing and failing fixtures.

The gate reports formatting on changed lines and lint on changed lines or newly reported lint in the surrounding file. It leaves files untouched. A pure rename keeps its baseline. The initial inventory after making the two UI callbacks parseable was 264 scripts, 1,954 lint findings and 228 files with formatter differences. Line length accounted for 1,280 findings and declaration order for 574. Those counts describe the starting tree. Changes are checked against Git so resolving an old finding reduces the baseline for later PRs.

## Starting a rule check without generating a map

Scene-free ferry rules live in `tests/rules/`. Extend `res://tests/rule_test_case.gd`, call `check(condition, message)` for each expectation and `finish()` once the case completes. Run an individual case with `godot --headless --script tests/rules/ferry_voyage_test.gd`. Register new regression scripts in `tools/fast_ci.sh`. The inventory fixture checks every `*_test.gd` under `tests/`. The other suites cover session lifecycle, simulation, traffic, player UI and world rendering or geometry. Fixtures and shared drivers live in `tests/fixtures/` and `tests/support/`. Capture and measurement scripts live in `tools/`.

`TinyRegion` in [tests/support/tiny_region.gd](../tests/support/tiny_region.gd) builds two island towns and one ferry route in about 50 ms, laid out with the map generator's own dock, route and town helpers. `TinyRegion.build().start(root)` returns a running simulation in about half a second; call it from the first `_process` frame, once the tree is live. `TinyRegion.build(3)` gives three towns whose routes meet. Use it for a rule that needs real terminals, ferries or navigation. Keep the seed-123 launch for whole-game behavior.

## Watching the cost of a frame

`tests/world/frame_budget_test.gd` runs in the fast suite. It measures the median headless frame on seed 123 and divides it by a fixed piece of script work timed on the same machine, so the result compares across machines. The baseline ratio is about 1.65 on the hosted runner (1.9 on a slower cloud machine) and the budget is 2.3. When a change needs more per-frame work, raise the budget in that PR and say why.

`tools/frame_cost.gd` shows where the time goes, system by system, in about two minutes. Differences under about 0.5 ms are noise. Both run headless and draw nothing, so they cover scripts and scene updates only. Rendering cost needs a device and `tools/perf_probe.gd`.

### Measure frame pacing on an iPad

With the development build installed, use Xcode's device identifier and its bundle ID. Each invocation relaunches that app, loads seed 123, waits for a fresh player-camera capture and records a Game Performance Overview trace. The app returns to its menu after recording. Use a new output directory for each run. `BUILD_REF` records the source commit supplied by the tester.

    BUILD_REF="$BUILT_COMMIT" bash tools/capture_ipad_frames.sh "$DEVICE" "$BUNDLE_ID" grass /tmp/grass-run-1
    BUILD_REF="$BUILT_COMMIT" bash tools/capture_ipad_frames.sh "$DEVICE" "$BUNDLE_ID" terminal /tmp/terminal-run-1

`grass` and `terminal` are paused 20-second views. `follow` follows the first ferry at normal speed for 90 seconds. The optional fifth argument selects the game executable name if it differs from `Tideways`. Repeat both builds on each iPad, reverse their order for the second pair and give them comparable time to cool. Inspect `camera.png` to confirm the view. Report the device, OS, build, camera, run order and thermal state alongside the times.

`frames.csv` gives the frame-weighted mean interval, its equivalent FPS and GPU active time for each process, Metal layer and thermal state. The first two seconds of the trace are excluded. Windows crossing thermal boundaries have their own row. The trace contains system-wide Instruments data and can stay on the profiling Mac. To recalculate an existing single-run trace, use `python3 tools/ipad_frame_report.py /path/to/game.trace`.

The road and marine traffic diagnostics also run nightly on main, and on demand from the Actions tab.


During an experiment, run the narrow check that answers today's question. For a tiny text edit, reading the rendered text can be enough. During a refactor, first run a case on current behavior. Where a bug is reproducible, keep the failing case, fix the owner, then confirm the same case passes. When an agreed behavior changes, record the reason on the ticket and update the expectation in the same PR.

Before merging, run the fast suite on the combined change and inspect the hosted result. Run the longer relevant diagnostic when a change affects routing, vehicle dispatch or traffic priorities. Use a real device for gestures, layout insets, performance or signing when that is how the change can fail. A docs-only PR can use link and diff checks locally plus the shared hosted check.

When a test fails intermittently, retain the seed, input size, commit and first failure output. Replay the same input on the branch and main. A passing retry by itself leaves the failure unexplained. Give a recurring failure its own engineering ticket with a reproduction and the behavior at risk. On the normal weekly board pass, look for recurrent failures, tests that always pass despite broken behavior, slow checks and player bugs that escaped CI. Add a targeted negative example or move an expensive diagnostic to the appropriate run. Judge coverage by the important failures the suite catches; no line or branch coverage percentage is currently measured.

## What the evidence leaves open

The HUD flow exercises pointer and keyboard commands at two viewport sizes. The touch editor exercises emulated finger events. Both check the resulting UI state. Safe-area insets, direct touch gestures, rendered text quality, water appearance and thermal frame pacing require device or rendered checks. The fast suite samples generated maps, so a passing run does not establish that every generated seed is connected. The five-seed route audit on seeds 121–125 found 24 routes, zero flagged route shapes and two split networks. Treat connectivity as a design decision for the map being tested.

When reviewing a long-lived draft, check for new test scripts or measurement probes. A regression test needs a failing outcome and successful completion that the runner can observe. A measurement-only probe can remain a named diagnostic with an interpretation of its output. Keep checks meaningful as features change; adding an assertion purely to increase a count gives the next verifier little evidence.
