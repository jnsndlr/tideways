# How the running game fits together

## How a session starts today

The title screen sends **Play** and **Sandbox** through `LoadingScreen.open`. The loading screen owns the transition and reports load failure to the menu. Play supplies the authored layout and an opening or mission scenario. Sandbox supplies a seed. [RegionEntryState](../scripts/region_entry_state.gd) keeps the generated seed, authored selection and editor state across scene replacement. Both scene scripts extend `WorldSession` and pass their inputs to its typed startup methods. Direct scene loads used by tools can run the same stages synchronously. [Menu](../scripts/ui/main_menu.gd) · [LoadingScreen](../scripts/ui/loading_screen.gd) · [Main Map](../scripts/main_map.gd) · [Sandbox](../scripts/sandbox.gd)

The [WorldSession](../scripts/world_session.gd) scene root is the **composition root**. It runs the supplied generation job, builds the terrain and world, prepares marine charts, constructs the simulation and connects the camera and HUD. Its exit handler cancels outstanding work and joins the data thread. Main Map adds its authored-region editor after the world is ready. [SessionDiagnostics](../scripts/session_diagnostics.gd) applies capture and demo options when the world is ready. The load recovery and shutdown tests cover failure, menu return and quit. [Region load recovery](../tools/region_load_recovery_test.gd) · [Generation shutdown](../tools/generation_shutdown_test.gd) · [Simulation shutdown](../tools/simulation_shutdown_test.gd)

## Current state owners

| --- | --- | --- |
| Region and terrain | MapGenerator produces MapData with islands, towns, slips, routes and harbours. Terrain supplies heights. WorldBuilder consumes geography for meshes. Simulation consumes it for traffic. | The authored and generated paths supply the same data type. Opening a purchased terminal changes its town’s built flag in Simulation.open_terminal. World and UI code consume that result. |

| Input, panels and camera | CameraRig owns the view. FleetPanel displays the list and emits the selected ferry. ## Trace a fleet purchase

1. The player selects a size in Fleet. The panel queries availability and emits `buy_requested(size)` on confirmation. HUD connects that signal to `_buy_ferry` and calls `Simulation.buy_ferry`. [Fleet panel](../scripts/ui/fleet_panel.gd) · [HUD](../scripts/ui/hud.gd)
2. Simulation delegates to `FleetMarket.buy_ferry`. The market checks the berth and available cash again, creates the ferry and plans the tow. A failed tow plan removes the new ferry before any charge. On success the market calls `CompanyLedger.spend`, registers the tow and emits `ferry_added`. The HUD selects the returned ferry. Keep a change to purchase eligibility in the market so a stale panel offer cannot bypass it. [Simulation](../scripts/sim/simulation.gd) · [FleetMarket](../scripts/sim/fleet_market.gd) · [CompanyLedger](../scripts/sim/company_ledger.gd)
3. The Fleet UI regression starts from Play, tries an unaffordable class, buys one $30,000 ferry, opens Finances and checks the single debit. The simulation regression follows the boat through delivery, service, lay-up, sale and tow-away. A change to the purchase rule can therefore be verified through both its owner and its player-facing entry. [Fleet purchase UI test](../tools/fleet_purchase_ui_test.gd) · [Fleet purchase lifecycle test](../tools/fleet_purchase_test.gd)

## Refactoring while the game grows

Start with the behavior that has to survive the change. Protect it with the smallest meaningful check, then move the state and the decisions that change it together. A second copy of a rule, a dependency on an unrelated scene, or two authors repeatedly colliding in a file are good reasons to split code. Keep the next change small enough to compare before and after. Use the [coverage map](verification.md) to choose that comparison.

## Boundaries to watch

- The departure board queries the live fleet for ferries serving that terminal; equal times retain fleet order. Shared-route service can put two ferries on one route. Exercise opposing traffic and near-simultaneous calls at the same berth when changing dispatch or manoeuvre rules. [Same-route passing](../tools/same_route_pass_test.gd) · [Shared slip](../tools/shared_slip_test.gd)
- MarineTraffic still combines spawn coordination, reservations and collision assessment. Protect the contested resource before moving one of those responsibilities. The regression for a removed harbour holder is an example. Splitting all vessels at once would make a change in traffic behavior harder to locate.
- Hud still owns several panels and the minimap. FleetPanel demonstrates the direction for another panel when its responsibilities start to interfere with selection or camera code. Keep the screen-coordinate UI flow green across the supported layouts.


## Identity at the authored-region and save boundary

The runtime uses dense IDs for islands, towns and routes. A company network record uses the region seed and stable keys for towns, route endpoints and individual hulls. Slip order within a lot still matters. The reader validates the topology before restoring fleet assignments. It can also read the older island-keyed form when the mapping to a town is unambiguous. [CompanyNetwork](../scripts/sim/company_network.gd) · [Company network regression](../tools/company_network_test.gd)

The full company snapshot and physical iPad reopen check remain separate work. See the [architecture decisions](architecture-decisions.md) for the durability boundary and the outstanding choice about a crossing in progress.
